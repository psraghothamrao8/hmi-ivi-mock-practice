1. Learn the Basics

Simple word list (jargon explained)

WordSimple meaning
HMIHuman Machine Interface – everything the driver sees or touches: screens, buttons, warning lights, voice.
IVIIn-Vehicle Infotainment – the middle touch screen: music, phone, maps, AC, settings.
Instrument ClusterThe screen/dials behind the steering wheel: speed, fuel, gear, warning lights.
ECUElectronic Control Unit – a small computer in the car. A car has many (engine ECU, door ECU, AC ECU…).
SignalOne small piece of data, e.g. "speed = 60", "door = open", "gear = R".
CAN busThe "wire road" ECUs use to send messages to each other. Think of it as a WhatsApp group for car computers.
CAN IDThe "name tag" of a message, like 0x3F0. It tells everyone what the message is about (e.g. speed).
DBC fileA "dictionary" file. It says: CAN ID 0x3F0, bytes 0–1 = speed, multiply by 0.01 = km/h. Without it, the data looks like random numbers.
GatewayA "post office" ECU that passes messages between different networks in the car (and to the IVI).
Android Automotive / AndroidThe operating system running many IVIs (like Android on a phone).
Signal simulationWe can't always sit in a real car. A tool pretends to be the car and sends fake signals ("speed = 120") so we can see what the screen does. Real tools: Vector CANoe, CANalyzer, PCAN, or the customer's own tool. (Page 2 has a mock one.)
Requirement / SpecA written rule: "When the door is open the door icon must show." We test against this.
Test caseA written recipe: steps + expected result.
Defect / BugActual result is different from expected result.
Regression testingAfter a fix, re-check old things to be sure nothing else broke.
Smoke testingQuick check on a new build: "does it start and do the main things work?" If not, stop testing.
Test automationA script does the test steps instead of a human. You run it and read the result.
Log / TraceA diary the software writes while running. When something fails, logs tell why. Evidence for the developer.
Build / Software versionA numbered copy of the software. Always write the build number in a defect.
Customer proxy teamPeople who represent the customer (the car company) and talk to you about test runs and issues.
Driver distractionSafety rule: while the car is moving, some things (typing on screen, videos) must be blocked.

How data travels (you wrote this in your resume – know it!)

ECU→CAN bus→Gateway→IVI→Android→HMI screen

Example, in plain words: The car is moving → the engine ECU measures speed = 60 km/h → puts it in a CAN message with ID 0x3F0 → the gateway forwards it → the IVI/cluster software reads it → an Android app draws "60" on the screen.

Why testers care: If the screen shows a wrong number, the problem can be in any step. You help find where by checking logs: Was the message sent? Was it received? Was it shown?

Two screens you will test

Instrument cluster (behind steering wheel)

  • Speed, RPM, fuel, temperature
  • Gear: P R N D
  • Warning lights: seatbelt, door, engine, low fuel, tyre pressure
  • Turn signals (indicators), high beam
  • Safety critical → wrong info here is usually high severity

IVI (centre screen)

  • Media: radio, USB, Bluetooth music
  • Phone: calls, contacts, Bluetooth pairing
  • Navigation (maps)
  • Climate (AC), Settings, language, themes
  • Rear camera when in reverse gear

What you actually check (HMI test checklist)

  1. Function – does the button do what it should?
  2. Display – correct text, spelling, icon, colour, unit (km/h vs mph, °C vs °F), alignment; nothing cut off or overlapping.
  3. Signal reaction – change a signal → does the screen react correctly and quickly?
  4. State – what happens with Ignition ON/OFF, gear changes, phone connected/disconnected?
  5. Timing – delays, freezes, slow loading. (Rule of thumb: a tap should react in about 1 second.)
  6. Languages and themes – day/night mode, translations, long German words.
  7. Negative tests – wrong or empty input, pressing buttons very fast, unplugging while playing.
  8. Boundaries (edge) – minimum/maximum values: volume 0 and 30, temperature 16 and 28.
  9. Interruptions – a call comes while music is playing; reverse gear while navigating.
  10. Safety – locks while driving.
Words from your resume: positive = correct input works; negative = wrong input is handled safely; edge = limits; explicit = written in the requirement; implicit = not written, but any user expects it (e.g. the app should not crash).

ADB and Logcat (you listed these – be ready)

ADB (Android Debug Bridge) = a command-line tool on your laptop that talks to an Android device (the IVI) over USB or network. Logcat = shows the Android log diary live.

adb devices                      # is the IVI connected? lists devices
adb shell                        # open a command window inside the IVI
adb logcat                       # live logs (very long!)
adb logcat -c                    # clear old logs BEFORE reproducing the bug
adb logcat -v time > bug.txt     # save logs with time into a file (attach to defect)
adb logcat *:E                   # only Errors
adb logcat | findstr Bluetooth   # filter lines (Windows). On Linux/Mac use grep
adb logcat -b crash              # crash buffer
adb bugreport                    # big zip with everything, for developers
adb shell screencap -p /sdcard/s.png ; adb pull /sdcard/s.png   # screenshot
adb shell screenrecord /sdcard/v.mp4                            # screen video
adb shell getprop ro.build.version.release   # Android version

Log levels (low → high): V verbose, D debug, I info, W warning, E error, F fatal. Look first for E, FATAL EXCEPTION, and ANR (App Not Responding = the app froze).

Good bug-evidence routine: 1) clear logcat 2) start screen recording 3) do the steps 4) when the bug appears, note the exact time 5) save logcat 6) attach video + log + screenshot to the ticket.

Defect life cycle

New→Assigned→In Progress→Fixed→Retest→Closed

Other states: Reopened (still broken), Rejected / Not a bug, Duplicate, Cannot reproduce, Deferred (fix later). "Cannot reproduce" is the reason good steps + logs matter.

Test execution lifecycle (the JD mentions it)

  1. Get the build + requirements
  2. Smoke test the build
  3. Run planned test cases (manual + automated)
  4. Mark each: Pass / Fail / Blocked / Not Run
  5. Log defects for fails
  6. Retest fixes + regression
  7. Daily/final test report: total, passed, failed, blocked, open defects, risks

Blocked = cannot run because something else is broken (e.g. Bluetooth won't pair, so call tests are blocked).

Reading an automation failure (key point in the JD)

When an automated test fails, ask in this order:

  1. Environment problem? Device not connected, wrong build, tool crash, network. → Re-run once.
  2. Test script problem? Script clicks an old button name, or waits too short. → Tell the automation owner / customer proxy.
  3. Real product bug? Same failure again; logs show an app error or wrong value. → Raise a defect with logs.
  4. Flaky? Passes sometimes, fails sometimes. → Run 3–5 times, report the pass rate.
Say this in the interview: "I never just write 'test failed'. I write what failed, expected vs actual, the log lines, how many times it repeated, and the impact."
